# 飲み会集合場所決めアプリ 要件定義書

## 1. 概要
参加メンバーそれぞれの「直前の活動場所の最寄駅」を入力すると、
- 各メンバーからの距離をもとに「みんなが集まりやすい駅」を3つ提案
- 各駅について、指定ジャンルの店を口コミ評価順に3つずつ表示
するPWA。

---

## 2. 機能要件

### 2.1 入力
- 参加メンバーの人数（可変、2〜10人程度）
- 各メンバーの最寄駅名（駅名オートコンプリート推奨）
- 店のジャンル選択（複数選択可）: 居酒屋 / 焼肉 / しゃぶしゃぶ / 寿司 / その他自由入力
- （任意）集合したい時間帯（店の営業時間フィルタに使う）

### 2.2 集合場所の算出

**方式：直線距離ベース**（当初の「電車所要時間ベース」から変更。理由は後述）

- 各メンバーの最寄駅から「候補駅」までの**ハバサイン距離（大圏距離）**を算出
- 候補駅は主要ターミナル駅・入力駅周辺の駅をある程度の範囲でリストアップ
- 評価指標：全員の距離の「合計」または「最大値」が小さい駅を上位に。両方の指標をUI上で切替
  - 合計最小 = 全体の移動コストが少ない
  - 最大値最小 = 一番遠い人の負担を抑える（不公平感を減らす）
- 上位3駅を提案

飲み会の集合場所決めという用途では、分単位の正確さよりも
「だいたい全員の中間にある駅が数件挙がる」ことのほうが価値が高いため、この割り切りで要件を満たす。

#### 【重要】なぜ電車の所要時間を使わないのか（再調査不要）

Routes API の `travelMode: TRANSIT`（ComputeRouteMatrix / ComputeRoutes）は
**日本国内では動作しない。**

- Google の公式ドキュメントに「ルートサービスは交通機関対象リストの全事業者をサポートするが、**日本は除く**」と明記されている
- Googleマップのアプリ/Webで日本の乗換案内が使えるのは、ジョルダン等とのパートナー提携によるもので、その権利はAPI利用者には及ばない
- そのため TRANSIT モードは、日本国内の座標に対して **HTTP 200 OK のまま `routes` が空**で返る（エラーではなく仕様上の ZERO_RESULTS 相当）

**切り分け済みの事実：**

- 同一キー・同一座標で `travelMode: DRIVE` に変えると正常に距離・時間が返る → **APIキー・Routes APIの有効化・課金設定はすべて正常**
- `routingPreference` は元から未指定。付けても外しても変わらない
- TRANSIT用フィールドマスク（`routes.legs.steps.transitDetails` 等）に変更しても空
- 住所ベース（例: 東京駅 / 品川駅）でも `geocodingResults` に正しい placeId が返る → ジオコーディングは成功している
- `computeAlternativeRoutes: true` でも変化なし
- 東京↔品川（同一路線・数分）、東京↔横浜、東京↔大阪（新幹線）すべてで同様に失敗 → 距離や経路の問題ではない

コード側のリクエスト形式の問題ではないため、**TRANSIT を使う方針自体を破棄した。**
将来同じ実装を試みて再度ハマらないよう、この経緯を残しておく。

### 2.3 店舗表示
- 提案された各駅について、選択ジャンルごとに口コミ評価順で上位3件を表示
- 表示項目：店名、評価（星）、レビュー件数、価格帯、写真、駅からの距離/徒歩分、営業時間、地図リンク

### 2.4 UI/UX
- モバイルファースト、PWA（ホーム画面追加、オフラインでも直前結果を閲覧可能）
- 駅名入力はオートコンプリート
- 結果は「駅カード（3枚）× 店カード（3枚）」のタブ or アコーディオン構成
- 距離ベースであることをユーザーに明示する（「電車で◯分」と誤認させない）

## 3. 使用する外部API（Google Maps Platform）

| 用途 | API |
|---|---|
| 駅名オートコンプリート | Places API - Autocomplete |
| 候補駅のリストアップ | Places API - Nearby Search |
| メンバー駅↔候補駅の距離 | **APIを使わない**（ハバサイン距離をサーバ内で計算） |
| 店舗検索（ジャンル別） | Places API - Text Search |
| 店舗詳細（評価・営業時間・写真） | Places API - Place Details |
| 地図表示（未実装） | Maps JavaScript API |

※ Routes API は使用しない（2.2 の理由による）。Google Cloud 側で無効化してよい。

**注意点**
- Places API は従量課金。APIキーはクライアントに直接埋め込まず、簡易バックエンド（Cloud Functions等）経由で叩く設計を推奨（キー漏洩・不正利用防止）
- Places APIの結果はキャッシュ期間に制限があるため、長期保存はしない（毎回取得 or 短時間キャッシュ）
- 距離計算はAPIを使わないため、人数・候補駅数が増えてもAPIコール数は増えない

## 4. アルゴリズム設計

### 4.1 候補駅のリストアップ
1. 全メンバーの最寄駅の緯度経度を取得
2. 全員の駅の重心（geometric centroid）を計算
3. 重心から半径◯km以内の主要駅、または各メンバー駅から一定時間圏内で重なるエリアの駅をピックアップ
   - シンプル版：重心付近の駅を10〜15件リストアップ
   - 発展版：各メンバーの駅から到達可能な駅集合の積集合をとる

### 4.2 距離マトリクスの算出
- 各メンバー駅 × 候補駅 のハバサイン距離をサーバ内で計算（外部API不要）
- 純粋関数として実装し、ユニットテストを持つ

### 4.3 スコアリング
```
score_sum(駅) = Σ(各メンバーの距離)
score_max(駅) = max(各メンバーの距離)
```
スコアが小さい順に並べ、上位3駅を採用。同着や僅差の場合は**全員の重心に近い駅**を優先する。

スコア集計は単位に依存しない形（`summarizeCosts()`）で切り出しておき、
将来 有料の乗換API を導入した際に距離の代わりに所要時間を渡せば済むようにしておく。

### 4.4 店舗検索・ソート
- 各候補駅の緯度経度を中心に、選択ジャンルでText Search（例:「居酒屋 渋谷駅」）
- 取得結果を `rating`（評価）× `user_ratings_total`（レビュー数）で加重ソート
  - 例：`weighted_score = rating * log(user_ratings_total + 1)`（レビュー数が少なすぎる高評価店を過大評価しないため）
- 上位3件を表示

## 5. 技術スタック案（PWA前提）

- フロントエンド：React + Vite（or Next.js）+ TypeScript
- PWA化：`vite-plugin-pwa`（Service Worker, マニフェスト自動生成）
- 状態管理：軽量なReact Context or Zustand
- スタイリング：Tailwind CSS
- バックエンド（APIキー保護用の薄いプロキシ）：Cloud Functions for Firebase など、サーバーレスで最小構成
- ホスティング：Firebase Hosting / Vercel

## 6. 画面構成（想定）

1. **メンバー入力画面**：人数指定 → 各人の最寄駅入力（オートコンプリート）
2. **ジャンル選択画面**：チェックボックスでジャンル選択、任意で時間帯指定
3. **結果画面**：
   - 候補駅3枚のカード（距離サマリー、地図ミニビュー）
   - 各駅タップで店舗3件表示（評価順）
   - 店タップで地図アプリに遷移 or 詳細モーダル

## 7. Claude Codeへの依頼時の補足事項
- Google Maps PlatformのAPIキー発行（**Places API (New)** を有効化）が事前に必要。Routes API は不要
- 課金設定（クレジットカード登録）が必須
- ローカル開発時は `.env` にAPIキーを格納し、リポジトリにコミットしないよう `.gitignore` 設定
- Firebaseプロジェクト作成（Blazeプランへの変更）を先に済ませておく

## 8. 開発フロー

**方針**：Claude Code（Web版）で叩き台のPRを作成 → ローカルにpullして仕上げ

1. **事前準備（ローカル/自分側）**
   - GitHubリポジトリを作成（空でOK）
   - Firebaseプロジェクト作成、Blazeプランに変更
   - Google Maps PlatformでAPIキー発行、必要API（Places API (New)）を有効化
   - `firebase-tools` をローカルにインストール（`npm install -g firebase-tools`）しておくと、pull後すぐ `firebase login` / `firebase init` に進める

2. **Claude Code（Web版）に依頼する内容の例**
   - 本仕様書（このMarkdownファイル）をそのまま貼るか添付
   - 「このリポジトリに対して、このPWAの叩き台を実装してPRを作成して」と依頼
   - APIキーそのものはWeb版に渡さない（`.env.example` のようなダミーファイルだけ用意させ、実キーはローカルで設定する）

3. **ローカルでの仕上げ**
   - 作成されたPRのブランチを `git fetch` → `git checkout <branch>` でpull
   - `.env` に実際のAPIキーを設定
   - `npm install` → `npm run dev` で動作確認
   - Firebase接続部分（`firebase init` 未実施なら手元で実行）、Cloud Functionsのデプロイ設定などを確認・調整
   - 動作確認できたらローカルから追加コミット → PRをマージ

4. **注意点**
   - APIキーや `.env` はPRに含めない・コミットしないよう、Claude Codeへの指示に明記する
   - Web版で生成されたコードはあくまで叩き台。候補駅の絞り込み（4.1）のパラメータやUIの細部はローカルでの仕上げ工程で詰める想定

- 駅データ.jp などの無料路線データを取り込み、「同一路線で乗換なしに行けるか」を加点要素にする
