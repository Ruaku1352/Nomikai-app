# 飲み会集合場所決めアプリ 要件定義書

## 1. 概要
参加メンバーそれぞれの「直前の活動場所の最寄駅」を入力すると、
- 電車移動の所要時間を考慮して「みんなが集まりやすい駅」を3つ提案
- 各駅について、指定ジャンルの店を口コミ評価順に3つずつ表示
するPWA。

---

## 2. 機能要件

### 2.1 入力
- 参加メンバーの人数（可変、2〜10人程度）
- 各メンバーの最寄駅名（駅名オートコンプリート推奨）
- 店のジャンル選択（複数選択可）: 居酒屋 / 焼肉 / しゃぶしゃぶ / 寿司 / その他自由入力
- （任意）集合したい時間帯（店の営業時間フィルタに使う）

### 2.2 集合場所の算出
- 各メンバーの最寄駅から「候補駅」までの電車所要時間（乗り換え込み）を取得
- 候補駅は主要ターミナル駅・入力駅周辺の駅をある程度の範囲でリストアップ
- 評価指標：全員の所要時間の「合計」または「最大値」が小さい駅を上位に。両方の指標をUI上で切替できると親切
  - 合計最小 = 全体の移動コストが少ない
  - 最大値最小 = 一番遠い人の負担を抑える（不公平感を減らす）
- 上位3駅を提案

### 2.3 店舗表示
- 提案された各駅について、選択ジャンルごとに口コミ評価順で上位3件を表示
- 表示項目：店名、評価（星）、レビュー件数、価格帯、写真、駅からの距離/徒歩分、営業時間、地図リンク

### 2.4 UI/UX
- モバイルファースト、PWA（ホーム画面追加、オフラインでも直前結果を閲覧可能）
- 駅名入力はオートコンプリート
- 結果は「駅カード（3枚）× 店カード（3枚）」のタブ or アコーディオン構成

---

## 3. 使用する外部API（Google Maps Platform）

| 用途 | API |
|---|---|
| 駅名オートコンプリート | Places API - Autocomplete |
| 電車所要時間（乗換考慮） | Routes API（Compute Routes, travelMode=TRANSIT）※Directions APIの後継、乗換時間込みで取得可 |
| 店舗検索（ジャンル別） | Places API - Text Search / Nearby Search |
| 店舗詳細（評価・営業時間・写真） | Places API - Place Details |
| 地図表示 | Maps JavaScript API |

**注意点**
- Routes API / Places API は従量課金。APIキーはクライアントに直接埋め込まず、簡易バックエンド（Cloud Functions等）経由で叩く設計を推奨（キー漏洩・不正利用防止）
- Places APIの結果はキャッシュ期間に制限があるため、長期保存はしない（毎回取得 or 短時間キャッシュ）
- 候補駅が多いと所要時間取得のAPIコール数が増える（人数×候補駅数）。候補駅は事前に絞り込む工夫が必要（後述4.2）

---

## 4. アルゴリズム設計

### 4.1 候補駅のリストアップ
1. 全メンバーの最寄駅の緯度経度を取得
2. 全員の駅の重心（geometric centroid）を計算
3. 重心から半径◯km以内の主要駅、または各メンバー駅から一定時間圏内で重なるエリアの駅をピックアップ
   - シンプル版：重心付近の駅を10〜15件リストアップ
   - 発展版：各メンバーの駅から到達可能な駅集合の積集合をとる

### 4.2 所要時間マトリクスの取得
- 各メンバー駅 × 候補駅 の組み合わせでRoutes APIをコール
- 人数5人・候補駅10件 なら最大50コール → 必要に応じて候補駅を事前に絞る（4.1で15件以下に抑える等）

### 4.3 スコアリング
```
score_sum(駅) = Σ(各メンバーの所要時間)
score_max(駅) = max(各メンバーの所要時間)
```
スコアが小さい順に並べ、上位3駅を採用。同着や僅差の場合は乗換回数が少ない方を優先、なども加点要素にできる。

### 4.4 店舗検索・ソート
- 各候補駅の緯度経度を中心に、選択ジャンルでText Search（例:「居酒屋 渋谷駅」）
- 取得結果を `rating`（評価）× `user_ratings_total`（レビュー数）で加重ソート
  - 例：`weighted_score = rating * log(user_ratings_total + 1)`（レビュー数が少なすぎる高評価店を過大評価しないため）
- 上位3件を表示

## 5. 技術スタック案（PWA前提）

- フロントエンド：React + Vite（or Next.js）+ TypeScript
- PWA化：`vite-plugin-pwa`（Service Worker, マニフェスト自動生成）
- 状態管理：軽量なReact Context or Zustand
- スタイリング：Tailwind CSS
- バックエンド（APIキー保護用の薄いプロキシ）：Cloud Functions for Firebase など、サーバーレスで最小構成
- ホスティング：Firebase Hosting / Vercel

---

## 6. 画面構成（想定）

1. **メンバー入力画面**：人数指定 → 各人の最寄駅入力（オートコンプリート）
2. **ジャンル選択画面**：チェックボックスでジャンル選択、任意で時間帯指定
3. **結果画面**：
   - 候補駅3枚のカード（所要時間サマリー、地図ミニビュー）
   - 各駅タップで店舗3件表示（評価順）
   - 店タップで地図アプリに遷移 or 詳細モーダル

---

## 7. Claude Codeへの依頼時の補足事項
- Google Maps PlatformのAPIキー発行（Places API, Routes API, Maps JavaScript APIを有効化）が事前に必要
- 課金設定（クレジットカード登録）が必須
- ローカル開発時は `.env` にAPIキーを格納し、リポジトリにコミットしないよう `.gitignore` 設定
- Firebaseプロジェクト作成（Blazeプランへの変更）を先に済ませておく

---

## 8. 開発フロー

**方針**：Claude Code（Web版）で叩き台のPRを作成 → ローカルにpullして仕上げ

1. **事前準備（ローカル/自分側）**
   - GitHubリポジトリを作成（空でOK）
   - Firebaseプロジェクト作成、Blazeプランに変更
   - Google Maps PlatformでAPIキー発行、必要API（Places / Routes / Maps JavaScript）を有効化
   - `firebase-tools` をローカルにインストール（`npm install -g firebase-tools`）しておくと、pull後すぐ `firebase login` / `firebase init` に進める

2. **Claude Code（Web版）に依頼する内容の例**
   - 本仕様書（このMarkdownファイル）をそのまま貼るか添付
   - 「このリポジトリに対して、このPWAの叩き台を実装してPRを作成して」と依頼
   - APIキーそのものはWeb版に渡さない（`.env.example` のようなダミーファイルだけ用意させ、実キーはローカルで設定する）

3. **ローカルでの仕上げ**
   - 作成されたPRのブランチを `git fetch` → `git checkout <branch>` でpull
   - `.env` に実際のAPIキーを設定
   - `npm install` → `npm run dev` で動作確認
   - Firebase接続部分（`firebase init` 未実施なら手元で実行）、Cloud Functionsのデプロイ設定などを確認・調整
   - 動作確認できたらローカルから追加コミット → PRをマージ

4. **注意点**
   - APIキーや `.env` はPRに含めない・コミットしないよう、Claude Codeへの指示に明記する
   - Web版で生成されたコードはあくまで叩き台。所要時間APIのコール数を絞る処理（4.1〜4.2）やUIの細部はローカルでの仕上げ工程で詰める想定
